### 2026-09-28 — Medea runtime QA feedback: recommendation tier outranks rarity

- **Status:** the previous Medea Mobalytics scoring candidate was exercised in a human-controlled DEV run beginning around 19:00 and ending around 19:49. The current QA run is complete, but the pilot is **not** closed: scoring policy and template validation are reopened before another runtime QA.
- **QA finding:** additive rarity could tie a recommended boon or make an unlisted boon appear equally preferred. The Hera offer visibly tied a Core recommendation with an unlisted Epic choice. The player must not be guided toward a lower-priority or unlisted choice solely because it is Rare/Epic/Heroic.
- **Separate Core-ownership question from QA:** Snow Queen (`Non-Core Boons`) appeared rank 1 while the Medea Core Cast boon Arctic Ring had not yet been acquired; the player had no Cast boon at that point. The tier/rarity rule below prevents Non-Core from outranking Core when both are compared, but does not by itself prevent a Non-Core from being rank 1 when no Core choice is currently offered. Before freezing the template contract, review whether runtime ranking should also account for missing owned Core targets (and what “Core completed” means across open slots). Dev should inspect and report the existing score/ownership semantics; do not invent a blanket all-Core acquisition prerequisite or implement this extra gate until its exact scope is approved. Include the Snow Queen → Arctic Ring progression as a runtime QA case.
- **Approved common rarity bonus:** Common `+0`, Rare `+1`, Epic `+2`, Heroic `+3`. Rarity is a secondary tiebreaker within a recommendation tier; it must never cross a recommendation-tier boundary. Implement comparison/scoring so every Core choice outranks every Non-Core choice, and every Non-Core choice outranks an unlisted choice, regardless of rarity. Avoid relying on the old additive `+2/+1/0` values, which do not guarantee this invariant.
- **Approved group policy:**
  - Boons: Core base `200`; Non-Core base `100`; absent/unlisted base `0`; add only the in-game rarity bonus above within that tier.
  - Daedalus Hammer Upgrades: listed base `200`, unlisted `0`; use the same rarity tiebreaker when the offered Hammer exposes rarity.
  - Legendary Boons: listed recommendations receive the maximum rank (the listed base plus the maximum Heroic bonus); unlisted choices do not receive the guide preference. They are already maximum rarity.
  - Duo Boons: listed `200`, unlisted `0`, with no rarity bonus. Keep an offer incomplete when its prerequisite/eligibility cannot be resolved; a spreadsheet listing alone does not prove the Duo is attainable.
  - Poms: if the owned boon being upgraded is Core, score `200`; otherwise apply the same guide-tier/rarity rule to the underlying listed boon where its source group is known. Do not double-count a boon merely because it appears in both Core Boons and Poms of Power.
  - NPC Offerings: listed `200`, unlisted `0`, gated by verified offer-source and item identity. Apply no rarity bonus unless the game provides a verified rarity for that offering and the implementation can preserve the tier invariant.
- **Template-contract gate:** revise the generic contract and generated-template validation/tests to encode the tier invariant and per-group behavior above before validating/finalizing the Medea template contract. Keep this policy source-aware; do not silently change unrelated existing profiles or their `BUILD_PREFERRED` behavior without an explicit compatibility plan.
- **Next order:** (1) update this roadmap and have Dev review the score model plus the separate Core-ownership/rank-1 question; (2) implement the approved tier/rarity contract, and seek a maintainer decision before implementing any additional Core-ownership gate; (3) offline regression tests for tier invariance across Common/Rare/Epic/Heroic, each listed group, Pom ownership, replacement, Duo unresolved prerequisites, and ties; (4) review the contract and generated Medea data against the approved sheet and any separately approved Core-ownership rule; (5) deploy and verify the exact build with the QA readiness gate; (6) repeat human runtime QA against real offers and logs, including the Snow Queen/Core Cast progression; (7) only then close the pilot and proceed to the remaining low-priority unevaluated-choice presentation decision.
